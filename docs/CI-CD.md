# CI/CD

Проект использует **GitHub Actions** для автоматизации проверок кода и управления версиями релизов.

Workflow находятся в:

```text
.github/
└── workflows/
    ├── ci.yml
    └── ci-tag.yml
```

## CI

Основной workflow находится в `.github/workflows/ci.yml`.

CI запускается в двух случаях:

* при `push` в любую ветку, кроме `main` и `release`;
* при создании `pull request` в `main` или `develop`.

Для `push` дополнительно настроен `paths-ignore`: изменения только в документации, лицензии, `.env.example`, `.version`, миграциях и некоторых конфигурационных файлах не запускают CI.

### Проверки Go

Основной job называется `checks-go` и выполняется на `ubuntu-latest`.

Последовательность проверок:

```text
Checkout
   │
   ▼
Create JWT keys
   │
   ▼
Setup Go
   │
   ▼
gofmt
   │
   ▼
go vet
   │
   ▼
go test
   │
   ▼
go build
```

### Checkout

Репозиторий загружается с помощью `actions/checkout`.

### JWT keys

Для тестов JWT-ключи передаются через GitHub Secrets.

Во время выполнения CI создаются временные файлы:

```text
secrets/
├── test-private.pem
└── test-public.pem
```

Ключи не хранятся в репозитории и создаются непосредственно в runner.

### Setup Go

Версия Go берётся из `go.mod`:

```yaml
go-version-file: go.mod
```

Также включён встроенный cache зависимостей Go.

Это позволяет CI использовать ту же версию Go, которая указана для проекта.

### Formatting

Проверяется форматирование всего Go-кода:

```bash
gofmt -l .
```

Если `gofmt` находит неформатированные файлы, job завершается с ошибкой.

CI не изменяет код автоматически — разработчик должен выполнить форматирование локально и закоммитить результат.

### Vet

Запускается стандартная статическая проверка:

```bash
go vet ./...
```

Она позволяет обнаруживать потенциальные ошибки, которые не выявляются обычной компиляцией.

### Tests

Все Go-тесты запускаются командой:

```bash
go test ./...
```

Для выполнения тестов необходимые параметры приложения передаются через GitHub Secrets.

В частности, используются настройки PostgreSQL, JWT, CORS, cookies и HTTP server.

### Build

В конце выполняется проверка сборки:

```bash
go build ./...
```

Таким образом, CI проверяет не только тесты, но и возможность собрать весь Go-код проекта.

## Docker CI

В `ci.yml` также присутствует отдельный job `checks-dockerfile`.

В текущем состоянии он **отключён**:

```yaml
if: false
```

Job подготовлен для отдельной проверки production Docker image.

Предполагаемый pipeline:

```text
Build Docker image
       │
       ▼
Start PostgreSQL
       │
       ▼
Start application container
       │
       ▼
Health check
       │
       ▼
Stop containers
```

Для сборки используется Docker Buildx и GitHub Actions cache.

После запуска контейнера выполняется health check приложения. Если приложение не становится доступным, выводятся его Docker logs, после чего job завершается с ошибкой.

Данный job можно включить после добавления полноценной проверки Docker-окружения в CI.

# Управление версиями

Для автоматического создания Git tags используется отдельный workflow:

```text
.github/workflows/ci-tag.yml
```

Он запускается после закрытия Pull Request в `main`.

Workflow продолжает выполнение только если:

* Pull Request действительно был merged;
* целевая ветка — `main`;
* исходная ветка — `develop`.

Таким образом, tag создаётся только после успешного слияния `develop` в `main`.

## Версия приложения

Версия хранится в корне проекта:

```text
.version
```

Используется формат Semantic Versioning:

```text
MAJOR.MINOR.PATCH
```

Например:

```text
1.4.0
```

Перед созданием tag workflow проверяет формат версии.

Некорректное значение `.version` приводит к остановке workflow.

## Создание tag

После успешной проверки создаётся Git tag с префиксом `v`:

```text
.version
   │
   ▼
1.4.0
   │
   ▼
v1.4.0
```

Перед созданием выполняется проверка, что такой tag ещё не существует.

Если tag уже существует, workflow завершается с ошибкой и предлагает обновить `.version`.

После этого tag создаётся и отправляется в GitHub:

```text
git tag v1.4.0
git push origin v1.4.0
```

## Защита от параллельного создания tag

Workflow использует GitHub Actions concurrency:

```yaml
concurrency:
  group: tag-version
  cancel-in-progress: false
```

Это предотвращает одновременное выполнение нескольких операций создания версии.

# Git Flow

Текущая схема работы с ветками предполагает следующий процесс:

```text
feature/*
    │
    ▼
 develop
    │
    │ Pull Request
    ▼
  main
    │
    ▼
  vX.Y.Z
```

`develop` используется как основная ветка разработки.

Изменения попадают в `main` через Pull Request:

```text
develop → main
```

После merge Pull Request workflow `ci-tag.yml` автоматически создаёт Git tag на merge commit.

Версия определяется содержимым `.version`.

Таким образом, создание релизного tag не требует ручного выполнения Git-команд.

# GitHub Secrets

CI не хранит чувствительные параметры непосредственно в workflow.

Конфигурация тестового окружения передаётся через GitHub Secrets:

```text
TEST_SERVER_*
TEST_POSTGRES_*
TEST_JWT_*
TEST_ACCESS_*
TEST_REFRESH_*
TEST_CORS_*
TEST_AUTH_COOKIE_*
TEST_LOGGER_*
```

Это позволяет использовать отдельную конфигурацию для CI, не добавляя credentials и приватные ключи в репозиторий.

Приватный JWT-ключ особенно важен: он существует только во время выполнения CI и создаётся из GitHub Secret непосредственно на runner.

# Ответственность workflow

| Workflow     | Назначение                                      |
| ------------ | ----------------------------------------------- |
| `ci.yml`     | Проверка Go-кода, тестирование и сборка         |
| `ci-tag.yml` | Создание Git tag после merge `develop` → `main` |

CI отвечает за **проверку качества изменений**, а `ci-tag.yml` — за **автоматизацию версионирования релизов**.

При этом Docker CI уже подготовлен в `ci.yml`, но пока отключён и может быть включён отдельно после необходимости в полноценной container-level проверке.
