## Обзор

В качестве основной базы данных используется **PostgreSQL**.

SQL-структура базы данных хранится в каталоге:

```text
db/
├── migrations/     # миграции схемы
├── queries/        # SQL-запросы для sqlc
└── ...
```

Схема базы данных изменяется только через миграции. Это позволяет последовательно воспроизводить состояние базы данных в development, test и production окружениях.

Доступ приложения к PostgreSQL осуществляется через repository layer и сгенерированный `sqlc` код.

Общий поток:

```text
Service
   │
   ▼
Repository
   │
   ▼
sqlc
   │
   ▼
PostgreSQL
```

## Таблица `users`

Таблица `users` содержит учётные записи пользователей.

Изначально идентификатор пользователя создавался как `SERIAL`, однако последующей миграцией был переведён на `UUID` с автоматической генерацией через `gen_random_uuid()`. ([GitHub][2])

Текущая структура:

| Поле            | Тип            | Ограничения                                | Назначение                 |
| --------------- | -------------- | ------------------------------------------ | -------------------------- |
| `id`            | `UUID`         | `PRIMARY KEY`, `DEFAULT gen_random_uuid()` | Идентификатор пользователя |
| `username`      | `VARCHAR(25)`  | `NOT NULL`, `UNIQUE`                       | Имя пользователя           |
| `email`         | `VARCHAR(254)` | `NOT NULL`                                 | Email пользователя         |
| `password_hash` | `TEXT`         | `NOT NULL`                                 | Хеш пароля                 |
| `role_id`       | `SMALLINT`     | `NOT NULL`, `FOREIGN KEY`                  | Роль пользователя          |
| `created_at`    | `TIMESTAMPTZ`  | `NOT NULL`, `DEFAULT now()`                | Время создания             |
| `updated_at`    | `TIMESTAMPTZ`  | `NOT NULL`, `DEFAULT now()`                | Время последнего изменения |

Начальная миграция создаёт `users` с `id`, `name` и `password_hash`. Далее поле `name` переименовывается в `username`, добавляются email, UUID и временные поля. ([GitHub][2])

### Email

Для email используется функциональный уникальный индекс:

```sql
CREATE UNIQUE INDEX users_email_unique_idx
ON users (LOWER(email));
```

Это означает, что следующие значения считаются одинаковыми:

```text
User@example.com
user@example.com
USER@EXAMPLE.COM
```

Уникальность проверяется без учёта регистра. ([GitHub][3])

## Таблица `roles`

Таблица `roles` содержит доступные роли пользователей.

Текущая структура:

| Поле   | Тип        | Ограничения               | Назначение         |
| ------ | ---------- | ------------------------- | ------------------ |
| `id`   | `SMALLINT` | `PRIMARY KEY`, `IDENTITY` | Идентификатор роли |
| `name` | `TEXT`     | `NOT NULL`, `UNIQUE`      | Название роли      |

При создании таблицы добавляется базовая роль:

```text
user
```

После этого в `users` добавляется `role_id`, ссылающийся на `roles.id`. ([GitHub][4])

Связь:

```text
roles.id
    ▲
    │
users.role_id
```

Одна роль может быть назначена множеству пользователей.

## Таблица `refresh_tokens`

Таблица `refresh_tokens` предназначена для хранения refresh sessions пользователей.

Текущая структура:

| Поле         | Тип           | Ограничения                                | Назначение                |
| ------------ | ------------- | ------------------------------------------ | ------------------------- |
| `id`         | `UUID`        | `PRIMARY KEY`, `DEFAULT gen_random_uuid()` | Идентификатор записи      |
| `user_id`    | `UUID`        | `NOT NULL`, `FOREIGN KEY`                  | Владелец токена           |
| `token_hash` | `VARCHAR(64)` | `NOT NULL`, `UNIQUE`                       | SHA-256 хеш refresh token |
| `created_at` | `TIMESTAMPTZ` | `NOT NULL`, `DEFAULT NOW()`                | Время создания            |
| `expires_at` | `TIMESTAMPTZ` | `NOT NULL`                                 | Время истечения           |
| `revoked`    | `BOOLEAN`     | `NOT NULL`, `DEFAULT FALSE`                | Отозван ли токен          |

Для `user_id` создаётся отдельный индекс:

```sql
CREATE INDEX idx_refresh_tokens_user_id
ON refresh_tokens(user_id);
```

Также индексируется `expires_at`, что позволяет эффективно работать с записями по сроку действия. ([GitHub][5])

### Хранение refresh token

В базе данных не хранится оригинальный refresh token.

Используется схема:

```text
Refresh Token
     │
     ▼
   SHA-256
     │
     ▼
 token_hash
     │
     ▼
 PostgreSQL
```

`token_hash` имеет длину 64 символа и является уникальным.

Это позволяет проверять refresh token без хранения его исходного значения в базе.

### Удаление пользователя

Для связи `refresh_tokens.user_id → users.id` используется:

```sql
ON DELETE CASCADE
```

Поэтому при удалении пользователя его refresh tokens автоматически удаляются PostgreSQL. ([GitHub][5])

## Связи между таблицами

### `roles → users`

```text
roles 1 ───────── N users
```

Одна роль может использоваться несколькими пользователями.

```text
roles.id
    │
    └── users.role_id
```

### `users → refresh_tokens`

```text
users 1 ───────── N refresh_tokens
```

У одного пользователя может существовать несколько refresh tokens.

```text
users.id
    │
    └── refresh_tokens.user_id
```

При удалении пользователя связанные refresh tokens удаляются автоматически.

## Миграции

Миграции находятся в:

```text
db/migrations/
```

Каждая миграция состоит из двух файлов:

```text
000001_init_db.up.sql
000001_init_db.down.sql
```

`up` применяет изменение, а `down` отменяет его.

Текущая последовательность миграций:

| Версия   | Миграция                       | Изменение                                     |
| -------- | ------------------------------ | --------------------------------------------- |
| `000001` | `init_db`                      | Создание `users`                              |
| `000002` | `add_email`                    | Добавление email и уникального индекса        |
| `000003` | `uuid_users`                   | Переход `users.id` с `SERIAL` на `UUID`       |
| `000004` | `add_refresh-token`            | Создание `refresh_tokens`                     |
| `000005` | `rename_user_column`           | `name` → `username`                           |
| `000006` | `add_table_roles`              | Создание `roles` и добавление `users.role_id` |
| `000007` | `add_create_at_in_users_table` | Добавление `created_at` и `updated_at`        |

Эта последовательность отражает эволюцию текущей схемы базы данных. ([GitHub][1])

### Принцип миграций

Новые изменения схемы добавляются новой миграцией.

Например:

```text
000007_...
000008_...
000009_...
```

Не следует изменять уже применённую миграцию. Если требуется изменить существующую структуру, создаётся новая миграция.

Это позволяет сохранять историю изменений схемы и воспроизводить базу данных с нуля.

## sqlc

SQL-запросы приложения находятся в:

```text
db/queries/
```

На их основе `sqlc` генерирует Go-код для работы с PostgreSQL.

Схема взаимодействия:

```text
db/migrations
      │
      │ PostgreSQL schema
      ▼
   sqlc config
      │
      ▼
  db/queries
      │
      ▼
 internal/db
```

Сгенерированный код содержит:

* модели таблиц;
* параметры запросов;
* методы выполнения SQL-запросов;
* интерфейс `Querier`.

Application code не должен писать SQL непосредственно внутри handlers или services.

Repository использует generated database layer и скрывает детали PostgreSQL от service layer.

## Правила работы с базой

При добавлении нового функционала рекомендуется соблюдать следующие правила:

1. **Изменение схемы — только через миграцию.**
2. **SQL-запросы хранятся в `db/queries`.**
3. **Go-код для SQL генерируется через `sqlc`.**
4. **Service не должен напрямую обращаться к PostgreSQL.**
5. **Repository предоставляет service необходимую абстракцию.**
6. **Пароли хранятся только в виде хеша.**
7. **Refresh tokens хранятся только в виде хеша.**
8. **Внешние ключи и ограничения должны находиться на уровне PostgreSQL.**
9. **Для часто используемых условий поиска создаются соответствующие индексы.**
10. **Применённые миграции не изменяются задним числом.**

Итоговая архитектура data layer:

```text
                 ┌──────────────┐
                 │   Service    │
                 └──────┬───────┘
                        │
                        ▼
                 ┌──────────────┐
                 │  Repository  │
                 └──────┬───────┘
                        │
                        ▼
                 ┌──────────────┐
                 │     sqlc     │
                 └──────┬───────┘
                        │
                        ▼
                 ┌──────────────┐
                 │  PostgreSQL  │
                 └──────────────┘
```
